1. System Overview & Goals

1.1 Purpose

Compliance Buddy (CB) is an autonomous security remediation pipeline that:

  1. Continuously scans Java codebases via SonarQube for security vulnerabilities (CWEs, OWASP Top 10).
  2. Uses GPT-4o to generate a code patch (unified diff) that remediates each vulnerability.
  3. Applies the patch to a local clone of the repository, runs build validation, and pushes a PR to GitHub.
  4. Conducts a 3-reviewer AI+human code review loop: GitHub Copilot, a configured human reviewer, and CB's own GPT-4o self-review with ACCEPT/REJECT checkboxes.
  5. On rejection, incorporates reviewer feedback into a re-generated fix — closing the remediation loop automatically.
✅ End-to-end tested and live The full pipeline from SonarQube scan → GPT-4o fix → validated patch → PR creation → CB review comment → ACCEPT/REJECT polling is operational on the kafka-micro-lab target repository.

1.2 Design Goals

GoalDesign Decision
Zero human toil for routine CVEsFully automated: scanner → LLM → patch → PR with no human in the loop until review time
No blocking in schedulersGitHub API + GPT-4o calls run in CompletableFuture.runAsync() — scheduler thread returns immediately
Cross-pod communicationMongoDB as the inter-service message bus; each service polls its own status slice (Spring events are in-process only)
Reviewer feedback loopRejection reason stored in cb_review_feedbacks; cb-agent reads it before re-generating the fix
ResilienceResilience4j circuit breaker + retry on all LLM and GitHub API calls; 10s connect / 30s read timeouts on RestClient
Local dev & CI parityEntire stack (SonarQube, MongoDB, all 8 services) runs in k3d on a developer laptop

1.3 Non-Goals (v1)

  • Multi-language support (Java only in v1)
  • Auto-merge without human ACCEPT (human must tick the checkbox)
  • SonarQube auto-scanner triggering (scans are scheduled; on-demand via REST API)

11. cb-scanner — Low-Level Design

11.1 Responsibilities

  • Poll SonarQube API every 5 minutes (configurable via SCANNER_POLL_INTERVAL_MS)
  • Page through all VULNERABILITY, BUG, CODE_SMELL issues for each configured project
  • Deduplicate via sonarIssueKey unique index; save new ones as DETECTED
  • Publish VulnerabilityDetectedEvent (in-process) after saving
  • Accept on-demand scan from cb-api (POST /api/v1/scans/{projectKey})

11.2 ScannerService — Key Method

@Scheduled(fixedDelayString = "${scanner.poll-interval-ms:300000}")
public void scheduledScan() {
    monitoredProjects.forEach(this::scanProject);
}

public int scanProject(String projectKey) {
    int page = 1, newFindings = 0;
    do {
        SonarIssuesResponse resp = sonarClient.getSecurityIssues(projectKey, page);
        for (SonarIssue issue : resp.issues()) {
            if (!vulnerabilityRepo.existsBySonarIssueKey(issue.key())) {
                Vulnerability vuln = issueMapper.toVulnerability(issue, projectKey);
                vulnerabilityRepo.save(vuln);
                eventPublisher.publishEvent(new VulnerabilityDetectedEvent(this, vuln));
                newFindings++;
            }
        }
        page++;
    } while ((page - 1) * 100L < resp.paging().total());
    return newFindings;
}

12. cb-agent — Low-Level Design

12.1 Responsibilities

  • Poll DETECTED vulnerabilities every 30s (via VulnerabilityPollerService)
  • For each: fetch similar past fixes via RAG (sentence-transformer embeddings → MongoDB vector search)
  • Fetch any unprocessed ReviewFeedback for re-fix scenarios
  • Call GPT-4o with system + user prompt; parse JSON-LD cb:Fix response
  • Mark feedbacks as processed; update status to FIX_GENERATED; fire FixGeneratedEvent

12.2 Fix Generation Flow

@Async("cbAgentExecutor") @EventListener
public void onVulnerabilityDetected(VulnerabilityDetectedEvent event) {
    vulnerabilityRepo.save(vuln.withStatus(IN_PROGRESS));

    List<Fix> ragFixes = ragService.retrieveSimilarFixes(vuln);
    List<ReviewFeedback> feedbacks =
        reviewFeedbackRepo.findByVulnerabilityIdAndProcessedFalse(vuln.id());

    String rawFix = callLlmWithFallback(vuln, ragFixes, feedbacks);
    Fix fix = parseFix(rawFix, vuln);
    fixRepo.save(fix);

    feedbacks.forEach(f -> reviewFeedbackRepo.save(f.withProcessed()));
    vulnerabilityRepo.save(vuln.withStatus(FIX_GENERATED));
    eventPublisher.publishEvent(new FixGeneratedEvent(this, vuln, fix));
}

12.3 RAG Retrieval Service

  • Posts vulnerability text to cb-python-embedder:8090/embed to get 384-dim vector
  • Queries cb_fixes with $vectorSearch (MongoDB Atlas) for top-3 similar BUILD_VALIDATED fixes
  • Falls back gracefully to empty list on local MongoDB (Atlas-only operator)

13. cb-patcher — Low-Level Design

13.1 Responsibilities

  • Listen to FixGeneratedEvent (in-process) — fired by cb-agent on the same pod
  • Apply the unified diff to /workspace/repo using a custom parser
  • Optionally apply gradlePatch to add new dependencies in build.gradle
  • Run BuildValidator.runBuild() — executes ./gradlew compileJava --no-daemon with 10-minute timeout
  • Mark fix as BUILD_VALIDATED or BUILD_FAILED; update vulnerability status
⚠️ Note on cross-pod events PatcherService listens to FixGeneratedEvent via @EventListener. In the current k8s deployment, cb-agent and cb-patcher are separate pods. The in-process event only fires within cb-agent. cb-patcher uses its own FixPollerService which polls for FIX_GENERATED status in MongoDB every 30 seconds as the reliable cross-pod trigger.

13.2 DiffApplier Algorithm

  1. Parse unified diff: extract file paths from +++ b/path headers and hunk headers (@@ -L,N +L,N @@)
  2. For each hunk, compute target line index with an offset accumulator (accounting for previous hunk's line count delta)
  3. Replace context+deleted lines with added lines via List.subList().clear() + List.addAll()
  4. Write modified line list back to file

13.3 Build Validation

ProcessBuilder pb = new ProcessBuilder("./gradlew", "compileJava", "--no-daemon");
pb.directory(new File(repoRoot));
pb.redirectErrorStream(true);
Process process = pb.start();
boolean completed = process.waitFor(timeoutMinutes, TimeUnit.MINUTES);
boolean success = completed && process.exitValue() == 0;

Build log is captured (up to 10 000 chars) and stored in Fix.buildLog.

14. cb-pr & AIReviewService — Low-Level Design

14.1 PRPollerService

  • Polls FIX_VALIDATED vulnerabilities every 60s
  • synchronized — ensures only one PR is created at a time (shared /workspace/repo)
  • For each FIX_VALIDATED: reset repo → apply diff → commit → push via JGit → create GitHub PR
  • After PR creation: fires async task for reviewer requests + AI review

14.2 JGit Push Flow

// 1. Reset to main/HEAD
git.checkout().setName("main").call();
git.reset().setMode(HARD).setRef("HEAD").call();
git.clean().setCleanDirectories(true).setForce(true).call();

// 2. Apply diff
applyDiff(repoRoot, fix.patchDiff());

// 3. Branch, commit, push
git.checkout().setCreateBranch(true).setName(branchName).call();
git.add().addFilepattern(".").call();
git.commit().setMessage("fix(" + vuln.cweId() + "): Auto-remediated by Compliance Buddy")
            .setAuthor("Compliance Buddy", "cb-bot@techseva.in").call();
git.push().setCredentialsProvider(new UsernamePasswordCredentialsProvider("token", githubToken))
          .setRemote("origin").call();

14.3 Async Reviewer + Review Dispatch

// After PR creation — fire-and-forget so @Scheduled thread returns immediately

14.4 AIReviewService — GPT-4o Review

  1. Fetch PR diff via GET /repos/:owner/:repo/pulls/:number with Accept: application/vnd.github.diff
  2. Call GPT-4o with system prompt (senior Java security engineer role) + diff content
  3. Parse JSON array of findings: [{"title","severity","description"}, ...]
  4. Build GitHub comment body with findings + ACCEPT/REJECT markdown checkboxes
  5. POST comment via POST /repos/:owner/:repo/issues/:prNumber/comments
  6. Save ReviewSession to MongoDB with returned comment ID and status PENDING (or NO_FINDINGS)

15. ReviewFeedbackPollerService — Low-Level Design

15.1 Poll Loop

@Scheduled(fixedDelayString = "${review.poll-interval-ms:60000}", initialDelay = 30000)
public synchronized void pollPendingReviews() {
    List<ReviewSession> pending = reviewSessionRepo.findByStatus("PENDING");
    for (ReviewSession session : pending) {
        String body = githubClient.getIssueCommentBody(owner, repo, session.githubCommentId());
        if (isAccepted(body))  reviewSessionRepo.save(session.withStatus("ACCEPTED"));
        else if (isRejected(body)) handleRejection(session, extractRejectionReason(prNumber));
    }
}

15.2 Checkbox Detection

GitHub renders - [ ] as a clickable checkbox. When clicked, GitHub edits the comment body in-place, replacing [ ] with [x].

SignalString to Match
ACCEPT[x] ✅ **ACCEPT** or [X] ✅ ACCEPT
REJECT[x] ❌ **REJECT** or [X] ❌ REJECT
Rejection reasonAny PR comment starting with REJECT: (case-insensitive)

15.3 Rejection Handling

  1. Query all PR comments looking for one starting with REJECT:
  2. Save ReviewFeedback{rejectionReason, processed=false}
  3. Close PR: githubClient.closePR(owner, repo, prNumber)
  4. Reset vulnerability: vuln.incrementRetryCount().withStatus(DETECTED)
  5. Save ReviewSession.withStatus("REJECTED")
  6. cb-agent polls within 30s, reads the unprocessed ReviewFeedback, augments GPT-4o prompt

16. Prompt Engineering

16.1 System Prompt (Fix Generation)

The system prompt establishes the AI persona and strict output rules:

  • Role: expert Java 17/Spring Boot security engineer, OWASP Top 10 specialist
  • CWE-specific remediation guidelines for 8 common CWEs (SQL injection, XSS, path traversal, hardcoded credentials, etc.)
  • Output format: JSON-LD cb:Fix object — exactly 6 required fields, no prose outside JSON
  • Each patched line must include trailing comment // CB-FIX: <cweId> — <strategy>

16.2 User Prompt Structure

## VULNERABILITY TO REMEDIATE
{vulnerability as JSON-LD cb:Vulnerability}

## SIMILAR VALIDATED FIXES (RAG top-3)  ← optional, if available

[{cb:Fix JSON-LD}, ...]

## ⚠️ PREVIOUS FIX REJECTED — REVIEWER FEEDBACK  ← only on re-fix
Your previous fix attempt was rejected. You MUST address ALL of the following:
1. {rejectionReason1}
2. {rejectionReason2}
Generate an improved fix that explicitly resolves every concern listed above.

## INSTRUCTION
Generate a JSON-LD cb:Fix object. Follow CWE guidelines. Respond ONLY with JSON-LD.

16.3 AI Review System Prompt (cb-pr)

  • Role: senior Java security engineer reviewing an auto-generated patch
  • Goal: identify remaining concerns, missed cases, side effects
  • Output: JSON array of findings (title ≤8 words, severity HIGH|MEDIUM|LOW, description ≤100 words)
  • Clean fix → return [] (empty array)

20. Key Patterns & Gotchas

20.1 The Poller Pattern (Critical)

Why pollers instead of Spring events across services? Spring's ApplicationEventPublisher / @EventListener is in-process only. In Kubernetes, each service runs in its own pod. Events published in cb-agent are invisible to cb-patcher or cb-pr. Every cross-pod trigger must go through MongoDB status polling.

branchName = "cb/fix-" + cweId.toLowerCase().replace(":", "-")
           + "-" + fixId.substring(0, 12)
// Example: cb/fix-cwe-89-a3b4c5d6e7f8

The 12-character fix ID suffix prevents branch name collisions between multiple fixes for the same CWE.
